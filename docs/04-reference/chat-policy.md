# 회원 채팅 대기열·한도 정책

이 문서는 **승인됐지만 아직 구현되지 않은 목표 동작**의 기준이다. 현재 등록된 API·5개 ORM 테이블과 별개이며, 이 문서 추가가 기능·배포 완료를 뜻하지 않는다. 현재 API 계약은 [API 기준](api.md), 현재 모델은 [DB 설계](database.md)에 있다. 일반 앱 제공자는 무료 mock을 유지한다. 실제 AI 연결·배포는 별도 검증 작업이다.

## 현재 구현과 목표의 경계

현재 메시지 상태는 `pending`, `completed`, `failed`, `interrupted` 네 가지다. 질문 POST는 제공자 생성과 연결되며 대화의 다른 pending은 `409 conversation_busy`다. 스트림 연결 중단은 현재 생성을 중단 처리한다. 30초 생성 기한, 다음 POST에서 60초 초과 pending 회복, 마지막으로 생성된 질문만 허용하는 D4 재시도가 구현되어 있다. PR #44 스트리밍과 PR #51 재시도는 병합됐다.

아래 목표에서는 접수·실행·구독을 분리한다. 현재 응답 예제나 DDL에 목표 상태를 추가해 구현됐다고 해석하지 않는다. 작업 API의 구체적인 경로·응답·상태 코드, DB 테이블·필드·제약과 마이그레이션 도구는 담당자가 설계·검토할 사항이다. 목표 작업 상태와 메시지 상태는 같은 개념이 아니다.

## 회원 한도와 정산

| 항목 | 승인 값 |
| --- | --- |
| 일일 한도 | 회원당 400회, KST 00:00 초기화 |
| 6시간 한도 | 회원당 100회, KST 00:00·06:00·12:00·18:00 초기화 |
| 이월 | 없음 |
| 차감 단위 | DB에 완성 답변 저장이 확정된 생성 1회 |

새 질문과 수동 재시도의 **접수 때 일일·6시간 잔량을 함께 원자적으로 예약**한다. 대기열 입장과 예약이 일부만 성공하지 않아야 한다. 완료 답변 저장이 확정되면 예약을 1회 차감으로 정산한다. 실패·중단·실행 전 취소·대기 만료가 종결되면 예약을 한 번만 환불한다. 결과가 불명인 동안 예약을 유지하고 결과를 조정한 뒤 정산 또는 환불한다.

정산·환불은 접수 당시의 일일·6시간 기간에 귀속한다. 초기화를 넘긴 옛 예약 환불은 새 기간의 잔량을 늘리지 않는다. 같은 키의 동일 요청을 재전송·재조회하면 새 예약·호출·차감 없이 기존 작업과 결과를 돌려주며, 남은 한도가 0이어도 가능하다. 사용자 한도 정산과 제공자 토큰·비용은 별개다. 제공자 호출이나 비용의 exactly-once를 보장하지 않는다.

## 입장과 실행 순서

- 회원 전체의 모든 탭·기기·대화에 걸쳐 실행 중 작업은 최대 1개다.
- 새 질문 대기는 최대 3개이며 실행 중 작업은 제외한다. 수동 재시도 대기는 회원당 별도 1개다.
- 실행 가능한 작업은 FIFO로 실행한다. 같은 대화의 실패 질문 재시도는 그 대화의 후속 질문보다 먼저 실행하지만 다른 실행 중 작업을 선점하지 않는다.
- 새 생성 시도 사이에는 최소 10초를 둔다. 자동 재시도는 없다. 같은 키의 결과 재조회는 새 생성 시도가 아니므로 이 간격으로 막지 않는다.
- AI 문맥은 접수 때 고정하지 않고 **실행할 때** 이전의 완료 질문+답변 쌍을 순서대로 읽고 현재 질문을 한 번 추가한다. 실패·중단·진행·부분 출력은 이력에 남기되 문맥에서 제외한다.

## 대기 취소와 만료

실행 전 작업만 취소할 수 있다. 실행 중 취소 API 동작이나 취소 버튼을 제공하지 않는다. 접수부터 5분이 지나면 아직 실행되지 않은 작업은 만료한다. 일시정지 중인 새 질문과 별도 재시도 대기도 포함하며, 정지·새로고침·재접속으로 기한을 연장하지 않는다. 실제 생성의 30초 기한은 대기 5분과 별도다. 실행 시작·취소·만료의 경합에서 하나의 결과만 반영하고 예약 환불을 중복하지 않는다.

## 실패, 재시도와 건너뛰기

실패·중단은 같은 대화의 후속 질문을 일시정지한다. 정지 중 새로 접수된 후속 질문도 정지하며 다른 대화는 실행할 수 있다. 실패 질문의 재시도가 성공하거나 사용자가 명시적으로 건너뛰면 후속을 재개한다. 재시도 실패·취소·만료는 정지를 해제하지 않는다.

재시도 대상은 **가장 최근 실행된 질문**이고 그 질문의 최신 답변이 `failed` 또는 `interrupted`여야 한다. 아직 실행되지 않은 뒤 질문의 접수만으로 재시도를 막지 않는다. 후속 질문이 실행을 시작한 뒤에는 앞 질문을 재시도할 수 없다. 수동 재시도 횟수는 제한하지 않는다. 각 새 시도는 새 키, 같은 시도 재전송은 같은 키를 유지한다. 새 시도는 한도·대기 자리·10초 간격을 검사한다. 화면은 서버가 허용한 동작만 표시한다.

## 연결, 로그아웃과 복구

연결 끊김·탭 닫기·새로고침·로그아웃은 서버 작업을 취소하지 않는다. 구독은 생성의 소유권이 아니다. 재접속하면 저장된 최종 결과를 조회한다. 놓친 delta 전체 재생은 이번 범위에 없다. 임시 delta는 저장 완료 답변과 구분하고 완료 저장 뒤에만 확정 결과를 보인다.

로그아웃은 해당 화면의 비공개 대화·임시 출력·구독을 지운다. 다른 회원에게 이 상태를 보여주지 않는다. 기존 access·refresh·logout 유효성 규칙을 바꾸거나 서버 작업을 취소하지 않는다. API는 접수·조회·구독·취소·재시도·건너뛰기 모두 검증된 회원과 소유권으로 제한한다.

서버 재시작 뒤 만료되지 않은 대기 작업은 복구한다. 실행 중이던 작업은 영속 완료 결과 또는 아직 유효한 실행과 조정한다. 해결되지 않는 실행은 중단으로 종결하며, 결과 불명 제공자 호출을 자동으로 다시 보내지 않는다. 늦은 이전 실행 결과가 종결 상태·새 시도·완료 답변을 덮어쓰지 못하게 한다. 제공자 쪽 생성·차감 중단은 보장하지 않는다.

## 구현과 검증 인계

공유 인터페이스 계획을 먼저 합의한 뒤 [#52 영속 대기열](https://github.com/next-stop-siren/Next-Stop-Siren/issues/52)의 영속 작업·실행 기반과 #15 한도 구현을 서로 순환 의존 없이 진행한다. [#53 API 통합](https://github.com/next-stop-siren/Next-Stop-Siren/issues/53)가 둘을 결합하고 화면의 실제 연동과 [#54 독립 검증](https://github.com/next-stop-siren/Next-Stop-Siren/issues/54)가 뒤따른다. [공정진행도](../02-team/development-flow.md)에 실제 이슈 번호·직접 선행을 정리한다. mock 화면 준비는 먼저 가능하지만 실제 API 완료로 보고하지 않는다.

스키마 적용·되돌림, 동시 입장·중복 정산·기간 경계·취소/실행/만료 경합·실패 정지·재시도·재시작·늦은 결과·소유권·재접속/로그아웃은 담당자의 구현 검사와 별도 독립 검증으로 확인한다. 이 문서 작업에서는 제품 코드·실행 SQL·DB·실제 AI를 변경하거나 실행하지 않았다.
