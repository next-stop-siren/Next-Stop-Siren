# 협업 흐름

PM은 GitHub Projects에서 목적·변경 범위·완료 기준·담당자를 적은 이슈를 관리한다. 작업자는 최신 `main`에서 `docs/환경-안내`, `fix/입력-검사`처럼 종류와 내용을 드러내는 이슈 브랜치를 만든다. `main`에 직접 개발하지 않는다. 범위가 바뀌면 구현 전에 이슈를 갱신한다.

커밋 제목은 Conventional Commit 형식으로 쓴다. 문서는 `docs: 개발 안내 보완`, 기능은 `feat: 질문 화면 추가`, 오류 수정은 `fix: 입력 오류 처리`, 검사는 `test: API 오류 검사 추가`, 도구·설정 정리는 `chore: 검사 설정 정리`처럼 적는다. 목적이 다른 변경은 분리하고 실제 이력을 다시 쓰지 않는다. 팀원마다 의미 있는 커밋을 최소 10개 남기되 숫자만 채우는 빈 커밋은 세지 않는다. PM의 실제 문서 기여도 동일하게 센다.

PR에는 연결된 이슈, 변경 동작, API·설정 영향, 실행한 검사와 결과, 남은 문제를 적는다. 담당자의 자체 확인 후 PM과 관련 담당자가 검토하고, 수정한 부분은 다시 확인한다. 공통 설정과 잠금 파일 변경은 PM이 검토한다. CODEOWNERS 지정만으로 검토가 강제되지는 않으므로 실제 리뷰와 브랜치 보호 규칙을 확인한다. 병합은 개인별 커밋과 PR 이력을 보존하는 병합 커밋 방식으로 한다.

향후 CI 게이트는 [품질 지침](quality.md)의 검사를 실행하고 실패한 PR의 병합을 막도록 설정한다. 병합 뒤 이슈와 문서를 실제 결과에 맞춰 정리한다.
