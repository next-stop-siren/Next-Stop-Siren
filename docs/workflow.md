# 협업 흐름

PM은 GitHub 이슈에 목적·변경 범위·완료 기준·담당자를 적어 관리한다. 진행 상태는 이슈와 PR에서 확인하며, Projects 보드를 사용하게 되면 PM이 연결 방법을 안내한다.

작업자는 최신 `main`에서 `docs/환경-안내`, `fix/입력-검사`처럼 종류와 내용을 드러내는 이슈 브랜치를 만든다. `main`에 직접 개발하지 않는다.

범위가 바뀌면 구현 전에 이슈를 갱신한다.

커밋 제목은 Conventional Commit 형식으로 쓴다. 예시는 다음과 같다.

| 변경 | 커밋 제목 예시 |
| --- | --- |
| 문서 | `docs: 개발 안내 보완` |
| 기능 | `feat: 질문 화면 추가` |
| 오류 수정 | `fix: 입력 오류 처리` |
| 검사 | `test: API 오류 검사 추가` |
| 도구·설정 정리 | `chore: 검사 설정 정리` |

목적이 다른 변경은 분리하고 실제 이력을 다시 쓰지 않는다.

팀원마다 의미 있는 커밋을 최소 10개 남기되 숫자만 채우는 빈 커밋은 세지 않는다. PM의 실제 문서 기여도 동일하게 센다.

PR에는 연결된 이슈, 변경 동작, API·설정 영향, 실행한 검사와 결과, 남은 문제를 적는다. 담당자의 자체 확인 후 PM과 관련 담당자가 검토하고, 수정한 부분은 다시 확인한다. 공통 설정과 잠금 파일 변경은 PM이 검토한다.

병합은 개인별 커밋과 PR 이력을 보존하는 병합 커밋 방식으로 한다.

작업 흐름의 예시는 다음과 같다. 다른 변경이 섞여 있으면 필요한 파일만 선택해 stage한다. 아래 push와 PR 단계는 팀원이 실제 작업할 때 수행하는 안내이며, 이 문서 변경에서 원격 작업을 실행했다는 뜻이 아니다.

```sh
git switch main
git pull --ff-only origin main
git switch -c docs/환경-안내
# 문서 수정 후
git add README.md docs/onboarding.md
git commit -m "docs: 개발 안내 보완"
git push -u origin docs/환경-안내
```

첫 push 뒤 GitHub에서 연결 이슈가 있는 PR을 열고 검사 결과와 미실행 사유를 적는다. PM과 관련 담당자가 실제 diff와 검사 증거를 확인한 뒤 권한 있는 사람이 병합 커밋 방식으로 병합한다. 현재 팀의 private Free 저장소에서는 `main` 보호 규칙으로 리뷰·필수 검사를 자동 강제할 수 없어 이 확인을 수동으로 운영한다.

CODEOWNERS 파일이나 CI 정의만으로 병합 차단이 생기지 않는다. 병합 뒤 이슈와 문서를 실제 결과에 맞춰 정리한다. 검사 범위는 [품질 지침](quality.md)을 따른다.
