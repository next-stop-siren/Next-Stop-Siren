# 협업 흐름

PM은 GitHub Projects에서 한 번에 확인할 수 있는 크기의 이슈를 만들고 담당자, 목적, 변경 범위와 완료 기준을 적는다. 최초 공통 설정은 [공통 개발 환경과 인계](environment.md)에 따라 검토·병합한 뒤, 담당자가 `main`에서 이슈 브랜치를 만들어 작업하고 PR로 변경을 공유한다.

작업과 버그는 각각의 이슈 양식으로 기록한다. 버그에는 재현 절차, 기대한 결과, 실제 결과와 발생 환경을 적는다. 이슈가 정리되면 담당자를 정하고 완료 기준과 확인 방법을 함께 확인한다. 범위가 달라지면 구현 전에 이슈 내용을 갱신한다.

브랜치는 최신 `main`을 기준으로 만들고 `docs/협업-양식`, `fix/로그인-오류`처럼 변경 종류와 내용을 짧게 드러내는 이름을 쓴다. 커밋 제목은 `docs: 협업 양식 추가`, `fix: 로그인 오류 수정`처럼 변경 종류와 목적을 적는다. 서로 다른 목적의 변경은 구분해 커밋하고, 실제 작업 이력을 임의로 다시 쓰지 않는다.

PR에는 연결된 이슈, 바뀐 동작, 화면과 서버의 요청·응답 형식에 미치는 영향, 실행한 로컬 확인 방법과 결과를 적는다. 환경 설정이나 문서가 바뀌면 함께 알린다. 담당자의 자체 확인 뒤 PM과 관련 담당자가 검토하고, 지적된 문제는 담당자가 수정해 다시 확인한다. 확인을 마친 변경은 개인별 의미 있는 커밋과 브랜치·PR 이력을 검토할 수 있도록 병합 커밋 방식으로 병합하는 것을 권장한다.

PR은 검토할 수 있는 크기로 유지하고, 검토가 필요한 부분과 남은 문제를 본문에 적는다. 검토자는 이슈의 완료 기준, 변경 범위, 사용자 영향과 확인 결과를 살핀다. 의견을 반영한 담당자는 변경 부분을 다시 확인하고 결과를 PR에 남긴다. 이슈의 완료 기준을 충족하고 필요한 확인과 검토가 끝나면 병합한다. 병합 뒤 이슈 상태와 관련 문서를 실제 결과에 맞게 정리한다.

팀원마다 의미 있는 커밋을 최소 10개 남긴다. PM의 실제 문서 기여도 의미 있는 개인 커밋으로 센다. 수를 맞추기 위한 빈 커밋이나 실제 이력과 다른 기여 기록은 만들지 않는다. 팀 역할과 개인별 작업 요약은 문서와 PR·커밋 이력에서 일치하게 유지한다.
