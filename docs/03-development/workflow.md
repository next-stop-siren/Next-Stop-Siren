# 협업 흐름

PM은 GitHub 이슈에 목적·변경 범위·완료 기준·담당자를 적어 관리한다. 진행 상태는 이슈와 PR에서 확인하며, Projects 보드를 사용하게 되면 PM이 연결 방법을 안내한다.

기존 팀 작업 이슈 #2–#21의 제목 형식은 `[작업] Sxx <설명 제목>`이다. 예를 들어 이슈 #3은 `S02`이며 제목은 `[작업] S02 사용자·Google 계정·로그인 세션 ORM 모델 만들기`다. `S01`–`S20`은 이 스무 작업의 고정 식별자다. 식별자 번호로 구현 순서나 완료 상태를 판단하지 말고 [공정진행도](../02-team/development-flow.md)의 직접 선행 조건과 해당 이슈·PR을 확인한다.

작업자는 최신 `main`에서 `docs/환경-안내`, `fix/입력-검사`처럼 종류와 내용을 드러내는 이슈 브랜치를 만든다. `main`에 직접 개발하지 않는다.

범위가 바뀌면 구현 전에 이슈를 갱신한다.

커밋 제목은 Conventional Commit 형식으로 쓴다. 예시는 다음과 같다.

| 변경 | 커밋 제목 예시 |
| --- | --- |
| 문서 | `docs: 개발 안내 보완` |
| 기능 | `feat: 질문 화면 추가` |
| 오류 수정 | `fix: 입력 오류 처리` |
| 검사 | `test: API 오류 검사 추가` |
| 도구·설정 정리 | `chore: 검사 설정 정리` |

목적이 다른 변경은 분리하고 실제 이력을 다시 쓰지 않는다.

팀원마다 의미 있는 커밋을 최소 10개 남기되 숫자만 채우는 빈 커밋은 세지 않는다. PM의 실제 문서 기여도 동일하게 센다.

PR에는 연결된 이슈, 변경 동작, API·설정 영향, 실행한 검사와 결과, 남은 문제를 적는다. 담당자의 자체 확인 후 PM과 관련 담당자가 검토하고, 수정한 부분은 다시 확인한다. 공통 설정과 잠금 파일 변경은 PM이 검토한다.

병합은 개인별 커밋과 PR 이력을 보존하는 병합 커밋 방식으로 한다.

작업 흐름의 예시는 다음과 같다. 다른 변경이 섞여 있으면 필요한 파일만 선택해 stage한다. 아래 push와 PR 단계는 팀원이 실제 작업할 때 수행하는 안내이며, 이 문서 변경에서 원격 작업을 실행했다는 뜻이 아니다.

```sh
git switch main
git pull --ff-only origin main
git switch -c docs/환경-안내
# 문서 수정 후
git add README.md docs/01-start/onboarding.md
git commit -m "docs: 개발 안내 보완"
git push -u origin docs/환경-안내
```

첫 push 뒤 GitHub에서 연결 이슈가 있는 PR을 열고 검사 결과와 미실행 사유를 적는다. PM과 관련 담당자가 실제 diff와 검사 증거를 확인한 뒤 권한 있는 사람이 병합 커밋 방식으로 병합한다. `main` 보호 규칙의 실제 적용 여부와 필수 검사·리뷰 조건은 병합 전에 GitHub 저장소 Settings에서 확인한다. 자동 차단 여부와 관계없이 PM과 관련 담당자는 검사 증거를 확인한다.

CODEOWNERS 파일이나 CI 정의만으로 병합 차단이 생기지 않는다. 병합 뒤 이슈와 문서를 실제 결과에 맞춰 정리한다. 검사 범위는 [품질 지침](quality.md)을 따른다.

## 선행 PR이 있는 작업

기본적으로 최신 `main`에서 브랜치를 시작한다. 아직 병합되지 않은 다른 PR의 변경이 있어야 작업할 수 있다면, PR 본문의 **선행 작업**에 선행 PR, 함께 포함된 선행 변경, 이번 PR에서 추가한 변경, 병합 순서를 적는다. 선행 작업이 없으면 `없음`으로 둔다.

선행 PR을 먼저 병합한 뒤 이번 작업 브랜치에 최신 `main`을 병합해 반영한다. PR의 변경 비교(diff)에 이번 작업에서 의도한 변경만 남는지 확인하고, 필요한 CI 검사 결과를 다시 확인한 뒤 이번 PR을 병합한다.

## PR 메타데이터 자동 연결

- PR 본문에 `Closes #3` 또는 `Fixes #4, #5`를 적는다. 같은 저장소의 전체 이슈 URL도 지원한다.
- PR 열기·수정·재열기·커밋 갱신 때 연결 이슈 라벨을 추가하고 기존 라벨은 유지한다. 모든 연결 이슈가 동일한 비어 있지 않은 마일스톤을 가지면 적용하며, 다르거나 없으면 기존 마일스톤을 유지한다. 재실행은 같은 결과를 유지한다.
- 이슈 라벨 변경 후에는 Actions의 **PR issue metadata → Run workflow**에서 양의 정수 `pr_number`로 다시 적용한다. 참조 제거로 라벨·마일스톤을 삭제하지 않는다.
- 일반 언급, 다른 저장소·PR URL, 주석·인용·코드는 제외한다. 복잡한 Markdown 중첩, 여러 줄 참조 목록, 링크 표시 문법은 지원하지 않는다. 연결이 없으면 변경하지 않는다.
- 접근·권한 오류는 작업 실패로 표시한다. 실패 전 일부 라벨 추가가 성공했을 수 있으며, 사람이 동시에 수정한 마일스톤은 자동 적용으로 덮어쓸 수 있다.

워크플로와 helper가 기본 브랜치에 병합되어야 동작한다. PR 코드를 체크아웃하지 않고 고정 SHA 액션으로 신뢰된 base 커밋의 helper를 읽는다(수동 실행은 현재 기본 브랜치). 최소 권한은 helper 읽기 `contents: read`, 이슈 조회 `issues: read`, PR 갱신 `pull-requests: write`다. 로컬 검사는 `node --test .github/scripts/pr-issue-metadata.test.cjs`이며 모의 API만 사용한다.
